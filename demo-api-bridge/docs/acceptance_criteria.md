# 検収条件

## PASS条件
1. **呼び出し元の認証**: `X-Bridge-Auth`ヘッダーが未指定または不一致のリクエストは401で即座に拒否され、以降の処理(ログ記録・upstreamへの転送含む)は一切行われないこと。
2. **スキーマ検証**: 旧形式スキーマに違反するペイロードは拒否(422)され、upstreamへ転送されないこと。
3. **冪等性**: 同一の`Idempotency-Key`を持つ複数のリクエストは、upstreamへの重複リクエストを発生させないこと。キャッシュされたレスポンスが返されること。
4. **マッピングの外部化**: フィールドマッピングのロジックは外部設定(`input/mapping_rules.json`)から読み込まれ、ハードコードされていないこと。
5. **レジリエンス**: Bridgeはupstreamの5xxおよび接続エラーを設定された上限回数までリトライするが、4xxエラーはリトライしないこと。
6. **タイムアウト制御**: upstreamが設定した時間制限を超えた場合、Bridgeはリクエストを中断し504 Gateway Timeoutを返すこと。
7. **ログのマスキング**: 機密フィールド(`api_key`、`password`等の認証情報に加え、`full_name`、`tel`等の個人情報)は構造化ログからマスキングされること。マスキング対象は認証情報に限定しない。
8. **Redisの認証**: Redisは無認証で待ち受けないこと。接続にはパスワードが必須であること。ホストや外部ネットワークへポートを公開しないこと(コンテナ間通信のみに限定)。
9. **キャッシュの暗号化**: 冪等性キャッシュに保存する値は、Redis自体の認証とは独立にアプリケーション側で暗号化されること。Redisの生データを直接読んでも内容が判読できないこと。
10. **未知の不具合に対する安全網**: 想定外の例外が発生した場合でも、HTTPレスポンス・ログのいずれにも、例外メッセージ本文やスタックトレース、リクエストの内容を含めないこと。記録するのは例外の型名のみとし、呼び出し元には汎用的な500エラーのみを返すこと。
11. **テストカバレッジ**: `pytest tests/`の実行結果が100% PASSであること。
12. **再現性**: 環境全体(Bridge、Redis、Upstreamモック)は`docker-compose up`のみで完全に再現できること。

## 対象外
* **複雑なメッセージブローカー**: モジュールを厳密に疎結合に保つため、Kafka、RabbitMQ、複雑なDead Letter Queue(DLQ)は含みません。
* **認証プロバイダ**: Bridgeは標準的なヘッダーに依存し、OAuthトークン自体の発行は行いません。

## 運用上の注意(実案件向け・本デモの範囲外)
* **TLS**: 本デモはHTTP/平文のRedisプロトコルで動作します。実際に個人情報が通信路を流れる本番環境では、Bridgeの手前にTLS終端(リバースプロキシ等)を置くこと、upstream先もHTTPSであることが前提になります。
* **暗号鍵の管理**: `CACHE_ENCRYPTION_KEY`・`BRIDGE_API_KEY`・`REDIS_PASSWORD`はいずれも環境変数のデモ用デフォルト値です。実運用では鍵管理サービス(Secrets Manager等)で管理し、`docker-compose.yml`に平文で書かないこと。
* **個人情報保護法対応**: 個人情報を業務委託として預かる場合、技術対策(本ドキュメントの内容)とは別に、委託先としての安全管理措置を文書化し、委託元との契約に反映する必要があります。
